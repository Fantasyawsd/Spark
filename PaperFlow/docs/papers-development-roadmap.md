## 1. 文档目标

本文记录 PaperFlow 论文页在完成 UI 原型后的功能缺口、技术边界、开发优先级和验收标准。

当前论文页使用内置 arXiv 种子数据，分类、搜索、点赞、收藏、评论、分享和 AI 已形成可测试的本地业务闭环。远程论文接口、账号、跨设备同步和服务端 AI 代理仍未实现。后续通过替换 Repository 或 Service 实现接入远程能力，不在页面组件中继续堆叠业务逻辑。

### 核心开发原则

本项目采用“本地功能先行，数据库后接入”的顺序：

1. 先使用现有 Demo 论文数据完成所有可见功能。
2. 分类、搜索、点赞、收藏、评论、转发和 AI 必须先在本地形成完整交互闭环。
3. 需要保留的状态先写入本地存储，不等待用户系统或远程数据库。
4. UI 只依赖 Repository、Service 和 Controller 接口，不直接依赖本地文件或远程 API。
5. 本地功能验收通过后，再将 Repository 的本地实现替换为数据库和服务端实现。

数据库不是第一阶段的前置条件。第一阶段的目标是让当前界面中的每个按钮都有真实、可测试的行为。

## 3. 当前实现边界

### 3.1 数据源

`PaperRepository` 当前只有同步的 `getAll()`，正式入口读取应用内置的 arXiv 种子数据：

```dart
abstract interface class PaperRepository {
  List<PaperRecord> getAll();
}
```

因此当前不支持：

- 远程论文数据
- 分页
- 刷新
- 加载状态
- 空状态
- 网络错误和重试
- 本地缓存

### 3.2 页面状态

`PaperController` 当前同时管理：

- 当前论文索引
- 单页和双栏模式
- 当前分类
- 自定义主题
- 点赞状态
- 收藏状态

论文流与互动状态已拆为 `PaperFeedController` 和 `PaperInteractionController`，评论由独立的 `PaperCommentController` 管理。正式入口注入文件型 Repository，本地状态可跨重启恢复；测试和预览可显式注入内存实现。

### 3.3 当前本地边界

- 搜索只检索本地 arXiv 种子数据，不访问远程索引。
- 分类、关注、点赞、收藏、评论、排序和分享计数均为本地状态，不跨设备同步。
- 相关论文使用结构化本地关系并可打开对应论文，但尚未接入真实引用图谱。
- 分享已接入平台服务；Android 系统分享面板仍需真机人工验收。
- 评论支持发送、回复、展开、点赞、删除、最新/最热排序和本地持久化，尚未接入账号或服务端。
- AI 对话和翻译由客户端开发配置直连 DeepSeek，正式发布前必须迁移到后端代理。

### 3.4 DeepSeek

DeepSeek 请求代码已经存在，但仍属于开发接入状态：

- API Key 通过 `--dart-define` 编译进客户端。
- 回复使用 OpenAI 兼容 SSE 流式输出，并分别展示思考过程和最终答案。
- 会话已按论文保存到本地，重新打开 Bottom Sheet 后可以恢复。
- 已支持请求取消和错误重试；限流和额度控制仍应由后端实现。
- AI 上下文只有论文元信息和摘要，不包含全文、图表或参考文献。

正式发布时不能将 DeepSeek API Key 放在 APK 中，应通过 PaperFlow 后端代理请求。

### 5.4 全局论文摘要翻译缓存

中文摘要翻译属于**论文级公共派生数据**，不属于某个用户的私有数据。数据库阶段接入后，任一用户首次完成某篇论文的摘要翻译，译文应写入 PaperFlow 的共享翻译库；其他用户再次查看同一论文、同一版本的中文摘要时直接读取已有译文，不再重复调用 DeepSeek。

当前本地阶段继续使用 `PaperTranslationRepository` 抽象和 `FilePaperTranslationRepository` 实现：

- 按稳定的论文 ID 保存设备本地译文。
- 同一设备再次查看时直接命中本地缓存。
- 保留手动重新翻译入口，便于处理错误译文或提示词升级。
- 展示层和 `PaperTranslationController` 不依赖本地文件格式，为后续替换远程实现保留边界。

数据库阶段采用“本地缓存 + 共享远程缓存”的两级查询：

```text
Flutter 本地缓存
  -> PaperFlow Backend 查询共享译文
  -> 未命中时由服务端创建或认领翻译任务
  -> DeepSeek 生成译文
  -> 服务端写入共享翻译库
  -> 返回客户端并写入本地缓存
```

共享翻译记录至少包含：

```text
paperId               稳定论文标识，例如 arXiv ID、DOI 或内部规范化 ID
sourceLanguage        原文语言
targetLanguage        目标语言
sourceAbstractHash    原摘要内容哈希，用于识别论文摘要修订
markdown              Markdown 格式译文
provider              翻译服务提供方
model                 实际使用的模型
promptVersion         翻译提示词版本
status                pending / completed / failed
createdAt / updatedAt 创建和更新时间
```

缓存与并发规则：

- 共享缓存唯一键至少由 `paperId + targetLanguage + sourceAbstractHash + promptVersion` 组成。
- 多个用户同时请求同一篇未翻译论文时，只允许一个服务端任务调用模型，其余请求复用进行中的任务或等待结果。
- 原摘要内容、目标语言或翻译提示词版本变化时生成新版本，不覆盖仍可追溯的旧译文。
- DeepSeek API Key、模型调用和共享译文写入权限只放在服务端；客户端不能直接写入“公共译文”。
- 网络不可用时优先展示设备上最后一次成功缓存的译文，并明确其可能不是最新版本。
- 用户手动重新翻译应请求服务端刷新，不应绕过版本和并发控制重复生成。

待实现项：

- [ ] 共享翻译表及版本字段
- [ ] 按论文 ID、摘要哈希和目标语言查询译文的接口
- [ ] 唯一约束、幂等写入和分布式任务去重

验收标准：第一位用户触发翻译并成功写入共享库后，其他用户查看相同论文版本时直接获得该译文，服务端不再发起新的 DeepSeek 翻译请求；离线时仍能使用本地缓存。

建议将列表摘要与完整详情分开，避免论文流一次加载大量全文：

```text
PaperSummary
  - 信息流必需字段

PaperDetail
  - 摘要、全文、作者、引用、资源链接

PaperInteractionState
  - 点赞、收藏、评论计数
```
