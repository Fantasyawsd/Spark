# PaperFlow 版本管理原则

> 状态：强制执行
> 最近更新：2026-07-31
> 当前仓库：`codex/papersSource`

## 1. 当前状态与反思

项目已经使用 Git，并且存在 `main` 与功能分支。但在本次检查前，工作区长期积累了大量未提交内容：28 个已跟踪文件发生修改，另外有约 70 个未跟踪文件，论文数据、AI、社区、搜索、持久化和视觉改造混在同一个工作区中，缺少可回滚的阶段边界。

这说明之前的版本管理只完成了“使用 Git”，没有完成“以可回滚、可审查的版本节点推进开发”。主要原因是：

1. 功能边界不断扩大，但没有在每个阶段结束时建立 checkpoint。
2. 新增文件没有及时纳入版本库，导致 Git 状态不能准确反映可交付范围。
3. UI、数据层、AI 接入和测试修改混在一起，提交粒度不利于定位回归。
4. 仓库当前没有配置远程仓库，因此本地提交可以回滚，但还不能作为异地备份。

本次处理方式：先保留当前完整工作区，建立一个明确的本地 checkpoint；从下一个功能开始按逻辑拆分提交。当前 checkpoint 是“论文功能与视觉改造阶段快照”，不把它伪装成单一小功能提交。

## 2. 分支原则

- `main` 只保留可发布或经过完整验证的基线。
- 每个功能、修复或设计迭代使用独立分支，命名格式：`codex/<领域>-<主题>`。
- 当前功能分支为 `codex/papersSource`，后续论文页、社区页和 AI 相关改动继续在功能分支完成。
- 不直接在 `main` 上进行大范围开发。
- 需要并行实验时，优先使用独立 worktree，避免覆盖另一个任务的未提交文件。

## 3. 提交原则

提交必须满足以下要求：

- 一个提交表达一个可以解释的变更意图。
- 提交前运行与变更相关的测试；UI 改动至少运行 `flutter analyze`、相关 Widget 测试和 Debug 构建。
- 提交信息使用统一前缀：
  - `feat:` 新功能
  - `fix:` 缺陷修复
  - `refactor:` 不改变行为的重构
  - `test:` 测试补充或修正
  - `docs:` 文档变更
  - `chore:` 工具、依赖或阶段 checkpoint
- 不提交构建产物、临时截图、调试日志、密钥和本地用户数据。
- 生成文件只有在项目明确要求追踪时才提交；其余通过 `.gitignore` 管理。
- 不使用含糊的“更新一下”“临时保存”等提交信息。

## 4. Checkpoint 与回滚

以下节点必须建立 checkpoint：

1. 完成一个 P0/P1/P2 阶段后。
2. 修改数据模型、持久化格式或 API 契约前。
3. 大范围视觉重构前。
4. 开始实验性重构或引入新依赖前。
5. 准备交给用户验收前。

Checkpoint 必须包含：

- 当前分支和提交 SHA。
- 变更摘要。
- 已运行的验证命令及结果。
- 已知未完成项和回滚风险。

优先使用 `git revert <commit>` 回滚已经共享的提交；只有在明确确认分支未共享且需要恢复工作区时，才使用 reset。禁止未经确认删除用户未提交的工作。

## 5. 验收与交付

- 用户验收前，工作区应保持干净；如果必须保留未提交实验，必须在交付说明中明确列出。
- 每次交付说明至少包含：分支、最新提交、验证结果、已知风险和下一步。
- 没有远程仓库时，必须明确说明“只有本地回滚能力”；配置远程仓库后，重要 checkpoint 才能推送形成异地备份。
- 版本号只在形成可发布版本时递增，不为了普通开发提交随意修改应用版本号。
- 发现用户要求回退既有行为时，先恢复行为，再重新设计视觉，不直接删除原有交互作为“简化”。

## 6. 当前执行记录

- 基线：`main`
