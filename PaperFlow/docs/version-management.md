# PaperFlow 版本管理原则

> 状态：强制执行
> 最近更新：2026-07-31
> 适用范围：PaperFlow 的代码、文档、测试、配置与发布产物

## 1. 当前状态与反思

PaperFlow 已经使用 Git，并存在 `main` 和功能分支，但后续开发没有持续形成可回滚、可审查的版本节点。当前长期分支只保留了早期少量提交，而论文 UI、社区、聊天、DeepSeek、搜索、持久化、数据源和测试等大量后续改动同时停留在工作区和暂存区。

这说明过去只完成了“仓库使用 Git”，没有建立“以版本节点推进开发”的流程。

### 1.1 失败原因

1. **把“不覆盖现有改动”误解成“不提交任何内容”。** 发现工作区已有用户或并行修改后，没有立即使用独立 worktree、独立分支或明确写集，而是继续叠加新改动。
2. **功能开始前没有确认文件归属。** 同一批文件被 UI、AI、数据层和测试同时修改，之后无法可靠判断每一行属于哪个任务。
3. **构建和打开界面代替了版本检查点。** 多次完成分析、测试和构建，但没有把“验证通过后形成可回退版本”纳入完成定义。
4. **高频 UI 评审没有一轮一版本。** 已接受方案、被否定方案和后续修正持续覆盖在同一个 diff 中，无法安全比较或恢复。
5. **长期综合分支承担了过多业务。** `codex/papersSource` 的实际范围已经远超名称含义，失去单一目标。
6. **没有脏工作区停止条件。** 未跟踪文件和跨模块改动持续增长，流程仍允许继续开发新功能。
7. **并行协作缺少物理隔离。** 多个开发者或 Agent 共用同一工作目录，口头约定无法保证文件和行的归属。
8. **暂存区被当作临时收纳区。** 大量跨功能文件一次性进入暂存区，但暂存不等于形成了可解释、可验证的版本。

版本管理失败是开发流程失败，不是最后少执行了一条 `git commit`。

### 1.2 当前历史状态的处理决定

当前开发进度已经远超最后可信提交，本次不再尝试：

- 将现有全部内容打包成“大 checkpoint”。
- 按猜测拆分历史提交。
- 修改提交时间线以伪造连续开发过程。
- 自动提交、推送、reset、clean 或回退现有工作区。
- 把当前暂存区直接视为可交付版本。

当前状态只记录为“历史边界已丢失的工作区快照”。是否将它确认为新的正式基线，必须由用户在明确检查范围后单独授权。

## 2. 开发前 Git 预检

每次开始功能、修复或重构前必须执行并阅读：

```text
git branch --show-current
git status --short
git diff --stat
git diff --cached --stat
git log -5 --oneline
```

开始修改前必须明确：

- 当前分支的单一目标。
- 工作区和暂存区现有改动的来源与所有者。
- 本任务允许写入的文件集合。
- 是否存在与本任务重叠的未提交改动。
- 当前 HEAD 是否是可信基线。

如果任一问题无法回答，不得继续直接修改该工作区。

## 3. 分支和 worktree 原则

### 3.1 一个功能一个短生命周期分支

分支名称必须表达单一目标，例如：

```text
codex/paper-pdf-entry
codex/ai-anthropic-stream
codex/community-card-density
```

禁止继续使用范围已经失真的长期综合分支承载新业务。功能完成并验证后应及时合并或关闭，下一项工作创建新分支。

### 3.2 并行开发必须使用独立 worktree

多个开发者、Agent 或并行任务不得在同一目录修改代码。每个任务必须具有：

- 独立分支。
- 独立 worktree。
- 明确且尽量不重叠的写入范围。
- 可独立验证和集成的提交。

集成通过 merge、rebase 或 cherry-pick 完成，不通过共享未提交文件完成。

### 3.3 脏工作区停止条件

出现以下任一情况时，停止新增功能：

- 无法说明现有改动的来源。
- 本任务需要修改已被其他任务修改但未提交的文件。
- 暂存区包含多个业务模块或来源不明的文件。
- 未跟踪文件已经跨越多个功能模块。
- 当前分支目标和实际改动范围不一致。

处理方式：从最后可信提交创建独立 worktree，只移植本任务明确需要的内容。未经用户授权，不得整理、提交或删除原工作区。

## 4. 提交原则

### 4.1 原子提交

一个提交只表达一个主要意图，并且必须可以独立说明、验证和回退。例如：

```text
feat: add PDF entry to paper reader
fix: keep AI tools visible on narrow screens
refactor: isolate paper feed filtering
```

同一提交不得混合：

- 无关 UI 调整和数据层重构。
- 功能实现和大范围格式化。
- 多个无法独立回退的业务能力。
- 来源不明的用户或其他 Agent 改动。
- 无关生成文件、缓存和本地配置。

提交大小不按行数机械判断，而按“是否只有一个原因、一个验证目标和一个回退单位”判断。

### 4.2 明确路径暂存

默认只允许：

```text
git add -- path/to/file1 path/to/file2
git diff --cached --stat
git diff --cached
git diff --check
```

默认禁止：

```text
git add .
git add -A
```

只有在任务从开始到结束独占干净工作区，并逐项审查全部文件时，才允许整体暂存。

### 4.3 提交信息

使用统一前缀：

- `feat:` 新功能
- `fix:` 缺陷修复
- `refactor:` 不改变行为的结构调整
- `test:` 测试补充或修正
- `docs:` 文档变更
- `chore:` 工具、依赖或明确授权的阶段基线

提交信息必须解释变更目的，禁止“更新一下”“临时保存”“大量修改”等无法审查的描述。

## 5. 阶段检查点

以下节点必须形成检查点：

1. 一个可独立工作的 tracer bullet 完成后。
2. 修改数据模型、持久化格式或接口契约前。
3. 大范围视觉重构前。
4. 开始实验性重构或引入新依赖前。
5. 用户确认一轮 UI 方案后。
6. 准备交付 APK、桌面包或用户验收版本前。

检查点必须记录：

- 分支和提交 SHA。
- 单一变更摘要。
- 已运行的验证命令和结果。
- 已知未完成项与回滚风险。

“代码已经运行”“界面已经打开”“测试曾经通过”都不能替代 Git 检查点。

## 6. UI 评审版本规则

高频截图驱动的 UI 开发必须执行“一轮一版本”：

1. 开始新方向前，当前已确认状态必须是可信基线。
2. 每轮只修改一个明确问题集合。
3. 用户接受后形成提交。
4. 用户否定时回退该轮提交或追加范围清晰的修正提交。
5. 不在同一个未提交 diff 中连续覆盖多个设计方向。

这样才能比较不同版本，并避免旧方案被无意覆盖后无法恢复。

## 7. 验证与提交门禁

提交前按顺序执行：

```text
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test <相关测试>
flutter test
flutter build <当前验收平台>
git diff --check
git diff --cached
```

如果完整测试被其他并行任务阻断：

- 必须记录失败项与本次改动无关的证据。
- 本功能定向测试必须通过。
- 不得声称“全部测试通过”。
- 集成前必须恢复完整测试通过。

## 8. 生成文件、密钥与本地数据

- 不提交 `build/`、临时截图、日志、缓存和用户运行数据。
- Flutter 自动生成文件只有在依赖变化确实要求时才提交。
- 不提交 API Key、Token、Secret、`.env.local` 或本机代理配置。
- 提交前搜索 `API_KEY`、`TOKEN`、`SECRET` 等敏感字段。
- 本地开发密钥通过用户环境变量或被忽略的本地配置提供。
- 任何包含密钥的客户端构建不得作为公开发布版本。

## 9. 回滚原则

- 已共享提交优先使用 `git revert`。
- 只有明确确认分支未共享时才考虑 reset。
- 未经确认不得 checkout、restore、clean 或删除用户未提交内容。
- 不得为了制造干净状态而丢弃来源不明的工作区文件。
- 回滚前必须记录目标提交、受影响功能和数据迁移风险。

## 10. 交付和远程备份

- `main` 只保留可发布或完整验证的基线。
- 用户验收前工作区应干净；存在实验改动时必须明确列出。
- 每次交付说明必须包含分支、提交 SHA、验证结果、已知风险和下一步。
- 本地提交只提供本机回滚能力；重要版本需要推送到远程形成异地备份。
- 版本号只在形成可发布版本时递增。

## 11. 完成定义

功能只有同时满足以下条件才算“版本完成”：

- 功能和测试达到验收要求。
- 代码结构符合项目原则。
- 变更已形成职责单一的提交。
- 提交没有混入其他任务或其他开发者的文件。
- 工作区剩余改动均能说明来源和归属。
- 分支可以安全合并、回退或交接。

如果尚未形成提交，只能称为“工作区实现完成”，不能称为“版本完成”。
